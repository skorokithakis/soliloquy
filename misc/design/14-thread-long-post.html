Why we did it

Two weeks ago I asked here if anyone had real numbers for async I/O in Postgres 18. Many of you helped, so this is the full report of what we measured and what we changed.

The reporting box runs one large rollup query each night. It reads about 40 GB from disk with a cold cache, and it must finish before the first dashboards load at 06:00. On Postgres 17 it took almost seven minutes, and the data grows each month.

The test setup

We made a copy of the reporting box so that the test could not hurt production:

  • Bare metal, NVMe storage, 64 GB RAM.
  • A restore of the production database from the night before.
  • The same rollup query, three runs for each setting, median time reported.
  • For the cold runs, a restart of Postgres and a drop of the OS page cache before each run.

We set effective_io_concurrency to 200 for all runs. With the default value the difference between the methods was much smaller, as @jules found too.

Results

io_methodcold runwarm runread MB/s sync6m 41s1m 12s102 worker4m 02s1m 11s169 io_uring3m 18s1m 12s207

Cold cache

This is the case that matters for us. With io_uring the query takes about half the time of sync. The worker method gets most of that gain and needs no kernel support, so it is a good fallback.

Warm cache

No difference. When the data is already in memory, the I/O method does nothing. If your slow queries run on a warm cache, this upgrade will not help you.

What went wrong

Two things cost us time:

  1. On the staging host, Postgres runs in a container. The seccomp profile blocked io_uring, and Postgres changed to worker with only one line in the log. Our first staging numbers were wrong because of this.
  2. Readahead on the data volume was 128 KB. An increase to 4 MB gave a larger gain for sync than for the other methods, so make that change before you compare.
Run SHOW io_method; after each restart. Do not trust the config file.

The config we shipped

io_method = io_uring
effective_io_concurrency = 200
maintenance_io_concurrency = 200

The nightly rollup now finishes in 3m 20s on production, which agrees with the test.

Open questions

We did not test the replica, which is on network storage. We also did not measure the effect on VACUUM. If someone has numbers for one of these, please add them below.

Thank you for the full report. The seccomp problem is the one that will catch most people, because nothing fails. The default Docker profile blocked these system calls for a long time, and many clusters still use an old copy of it.

One addition for the replica: on network storage the latency of each request is much higher, so I expect that worker and io_uring will be almost equal there. The number of requests in flight matters more than the method.
